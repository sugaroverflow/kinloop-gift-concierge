# Future Considerations

Non-MVP strategy and research direction. Nothing here is part of the current product path unless it later moves into `docs/architecture.md` or an execution journal entry.

## Why The MVP Is Constrained

The current app intentionally proves bounded autonomy before broader commerce automation:

- human review before external side effects
- visible data boundaries
- schema-validated Codex output
- Supabase-backed product memory
- local resilience
- inspectable audit paths
- safe channel modes

The product should earn more autonomy by proving reliability, consent, reversibility, and operational clarity first.

## Non-Submission Directions

Future versions may explore:

- recursive planning swarms
- delegated gift logistics
- long-term relationship memory
- collaborative household gifting
- autonomous negotiation agents
- adaptive escalation policies
- continuous preference learning
- richer merchant research and recovery integrations
- production OpenClaw gateway/VPS operations
- external MCP servers for consented tools and diagnostics

All require governance, consent, revocation, audit, and production operations before becoming user-facing features.

## Recursive Planning Swarms

Future planning agents could specialize in event research, vendor comparison, logistics, budget optimization, travel-aware gifting, household coordination, or shipping recovery.

Research-only pattern:

```txt
Primary orchestrator
-> specialized planning agents
-> trust/safety review
-> human-reviewed shortlist
```

MVP boundary:

- Do not build recursive autonomous swarms.
- Do not let build subagents become runtime product agents.
- Do not let any agent purchase, message, or negotiate independently.

## Delegated Gift Logistics

Autonomous purchasing remains out of scope. Any future delegated authority would need:

- explicit spending limits
- merchant research allowlists
- recipient/address verification
- revocation controls
- dispute handling
- payment and commerce compliance review
- cancellation windows
- audit-ready decision records

Even future autonomy should be bounded and policy-driven, not open-ended.

## Long-Term Memory

Long-term memory could improve relationship continuity only if it remains inspectable and correctable.

Future concepts:

- relationship summaries with provenance
- gift history and reaction memory
- avoid-list and sensitivity memory
- household/shared gifting preferences
- memory expiration and review cycles
- user-visible correction and deletion

Current boundary: Supabase is the product memory source of truth. File-backed memory supports inspectable repo context. Codex Memories are build-process recall only.

## Governance And Trust

Future autonomy should be gated by:

- consent scopes
- source evidence
- revocation paths
- audit logs
- raw private text redaction
- policy checks before external side effects
- explainable blocked states
- enterprise admin visibility

Strategic principle:

```txt
The product earns autonomy by proving reliability, consent, and auditability first.
```
